# 0009 — Waitlist storage: Postgres via Drizzle, own route handlers

- **Status:** Accepted
- **Date:** 2026-11-02

## Context

Task 012 must store waitlist sign-ups and survey answers. [ADR 0006](0006-landing-next-dokploy.md) already puts Postgres on the owner's Dokploy and the page in one Next.js container; [ADR 0007](0007-turnstile-waitlist.md) requires a server-side Turnstile check. The page is public, so the write path must resist bots, duplicate rows and strangers writing survey answers for someone else's email. The owner wants to read the list from a phone.

## Decision

- **Store:** one `signups` table in Postgres (Dokploy service), accessed with **Drizzle ORM** + the `postgres` driver. Schema in `apps/landing/src/db/schema.ts`; SQL migrations generated by drizzle-kit into `apps/landing/drizzle/` and checked in. The server runs pending migrations on start (`instrumentation.ts`).
- **Routes** (Next.js route handlers, `runtime = nodejs`): `POST /api/signup`, `POST /api/survey`, `GET /api/admin/export`.
- **Sign-up:** validate input, verify the Turnstile token with siteverify (`success`, `action = signup`, `hostname` = the site host), then insert. The email is trimmed and lowercased and is unique: a repeat insert does nothing and still answers success, so the UI shows the same panel and no duplicate row is made.
- **Survey:** only a new sign-up gets a survey token: an HMAC-SHA256 of the row id plus a 1 h expiry, signed with `SIGNING_SECRET`. `POST /api/survey` writes car and features only with a valid token, and only once. A repeat sign-up gets no token and sees no survey. Skip sends nothing.
- **Rate limit:** in memory, per IP (`X-Real-IP` from Traefik), sliding window: 5 sign-ups and 10 surveys per IP per 10 min. Over the limit: HTTP 429 and an inline error.
- **Export:** `GET /api/admin/export` behind HTTP Basic auth (password = `ADMIN_TOKEN`, compared in constant time; any user name). It returns a CSV; `?summary` returns platform, language, car and feature counts. Responses are `no-store` and `noindex`. Not linked anywhere.
- **Secrets** are runtime env on Dokploy, never build args or client code: `DATABASE_URL`, `TURNSTILE_SECRET_KEY`, `SIGNING_SECRET`, `ADMIN_TOKEN`.

## Consequences

- One service plus the Postgres service; no third-party form tool sees the emails.
- The rate limit resets when the container restarts and does not share state between containers. Accepted for one container; move it to Postgres or Traefik if the app scales out.
- Deleting a person's data on request is a manual SQL delete by the owner (documented in `apps/landing/CLAUDE.md`).
- A repeat sign-up cannot answer the survey again; the first answers stay.

## Alternatives considered

- **Prisma** — owner's usual stack, but its generate step and engine make the standalone image heavier for one table.
- **postgres.js with raw SQL** — smallest, but no typed schema or generated migrations.
- **Hosted form or list service (Google Forms, Mailchimp, Supabase)** — emails leave our server; owner prefers self-hosting.
- **Token in the export URL (`?token=`)** — easy, but the secret ends up in logs and browser history; Basic auth gives the same phone flow.
- **Rate limit in Postgres or Traefik** — survives restarts, but more code or config outside the repo for a single-container site.

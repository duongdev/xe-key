# Git workflow

The smallest workflow that keeps history readable. Solo today; assume a contributor could join tomorrow.

## Branches

- `main` — always green, always shippable.
- Feature branches off `main`, merged via PR (even solo, for the audit trail).

### Branch naming

```
<type>/t<NNN>-<short-kebab-name>     # when the work is a docs/tasks/ task
<type>/<short-kebab-name>            # ad-hoc chore/fix with no task
```

Types: `feat` (new capability), `fix` (bug), `refactor` (no behavior change), `docs`, `chore` (config/deps/tooling), `test`, `spike` (throwaway, never merges).

Examples: `feat/t003-adaptive-viewport`, `fix/t007-offset`, `refactor/extract-dedup`, `chore/biome-config`, `spike/ime-prototype`.

**Task IDs vs private PM IDs:** the `tNNN` prefix is the repo-internal task ID from `docs/tasks/NNN-*.md` — open-source-safe, stamp it in. **Never** include private PM-tool references (Linear/Jira/Notion); that metadata stays out of the repo entirely.

Enforced by the `branch-name-check.sh` PreToolUse hook.

## Commit messages

**Semantic title only. Lowercase. No body.**

```
<type>(<scope>): <description> (tNNN)
```

The ` (tNNN)` suffix makes every commit traceable to its spec; omit only for genuinely task-less chores. Private PM IDs never appear.

Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `test`, `perf`, `style`, `build`, `ci`, `revert`. Scope: the module/area affected. Description: imperative present, lowercase, no trailing period.

**Good:** `feat(notifications): add teams toast capture (t005)` · `fix(viewport): correct letterbox offset (t008)` · `chore: bump electron to 34`
**Bad:** `Fix bug` (vague, capitalized) · `wip: stuff` · `feat: add X and fix Y and update Z` (multi-thing)

Why a change was made goes in the **PR description**, not the commit body.

## Atomic commits

Each commit does one thing and leaves the system green. Squash merges into `main` are fine when a branch has WIP-style commits — the squash message follows the rules above. Prefer rebase + `--force-with-lease` on feature branches over merge commits; never rebase shared branches without coordination.

## Hard rules

1. **Never auto-commit.** Commit only when the user says "commit".
2. **Never auto-push.** Push only when the *current* message says "push" — prior approvals don't carry forward.
3. **Never attribute work to AI** — no `Co-authored-by`, no "generated by", anywhere.
4. **Never reference private PM IDs** in code, commits, branches, or PRs.
5. **Never `--no-verify` / skip hooks** unless explicitly asked.

## Pull requests

Even solo, every change to `main` goes through a PR — a self-review beat and an audit trail.

### PR template

```markdown
## What
One paragraph, plain language.

## Why
Motivation — link the task file or ADR.

## How
Brief technical summary. Modules touched. Contract changes if any.

## Tests
- [ ] Unit tests added/updated (pure logic)
- [ ] Manual smoke test performed (glue/IO surface)
- [ ] Visual review (if UI-touching)
- [ ] All quality gates green

## Docs
- [ ] Per-area docs updated
- [ ] ADR written (if architectural decision made)
- [ ] Task closed (status done, moved to done/)

## Out of scope
What this PR explicitly does not do.
```

### Self-review pass

Before opening a PR: re-read your own diff top to bottom; run the gates once more; verify doc updates match what changed; manually exercise the feature; then open it. A 10-minute self-review costs far less than merging a regression.
